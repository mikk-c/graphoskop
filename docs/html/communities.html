Communities

Communities: discovery of communities, quality of partitions of the nodes into groups, and maximal cliques.

block_model_communities() finds communities by fitting the stochastic blockmodels of the generators (nested, degree-corrected, plain, planted partition, mixed membership) to a network; infomap_communities() by compressing the description of a random walk on it (Infomap); label_propagation_communities() by letting nodes adopt the labels of most of their neighbors; leiden_communities() by maximizing modularity (or the constant Potts model) with the Leiden algorithm; hierarchical_random_graph_communities() by the consensus of hierarchical random graphs. Infomap and label propagation can also find overlapping communities (max_communities above 1), written as covers; bigclam_communities() finds overlapping communities by fitting the community affiliation model of BigCLAM, demon_communities() by merging the communities of the ego networks of all nodes, and oslom_communities() by keeping the statistically significant clusters. Link communities group the links instead of the nodes, so that nodes are in the communities of their links: hierarchical_link_communities() by hierarchical clustering of the links, line_graph_communities() by partitioning the line graph. The quality of any partition is measured by modularity(), by codelength(), the map equation of Infomap, and community by community by conductance(), internal_density() and out_degree_fraction(). Two partitions are compared by normalized_mutual_information(), adjusted_mutual_information() and adjusted_rand_index().

A partition assigns every node to a community, given either as the name of a node attribute (numeric or qualitative; its values are community labels) or as labels in a dictionary (or pandas.Series) indexed by input node id, or in a sequence ordered as the nodes of the network (component by component, by internal index: np.concatenate(net.node_ids)). Labels can be of any type; only equality matters. In multilayer networks every copy (entity, layer) has its own label, so a community can span several layers. A node in several communities has a list, tuple or set of labels (see Several values per node: overlapping communities): the partition is then a cover, for which modularity() is the overlapping modularity.

import graphoskop as gsk

net = gsk.load_network("edges.tsv", "nodes.tsv")         # nodes.tsv has a "party" column
gsk.modularity(net, "party")                             # partition from a node attribute
gsk.modularity(net, {"alice": 0, "bob": 0, "carol": 1})  # or from labels by node id
cliques = gsk.maximal_cliques(net)                       # node sets of the cliques of 3+ nodes
gsk.bigclam_communities(net, attribute = "cover")        # overlapping communities (BigCLAM)
gsk.demon_communities(net, attribute = "demon")          # overlapping communities from ego networks
gsk.oslom_communities(net, attribute = "oslom")          # statistically significant (overlapping) communities
gsk.block_model_communities(net, seed = 0)               # nested blockmodel: community, community_1, ...
gsk.hierarchical_random_graph_communities(net, attribute = "hrg")   # consensus dendrogram: hrg, hrg_1, ...
gsk.infomap_communities(net, attribute = "module")       # Infomap: module, module_1, ...
gsk.label_propagation_communities(net, attribute = "lpa") # label propagation
gsk.leiden_communities(net, attribute = "leiden")         # Leiden: maximum modularity
gsk.hierarchical_link_communities(net)                   # link communities: edge and node attribute link_community
gsk.conductance(net, "leiden")                           # quality of the communities found
gsk.normalized_mutual_information(net, "party", "leiden")  # similarity of two partitions

Cliques

graphoskop.maximal_cliques(net, component=None, min_size=3, batch_size=4194304)

Maximal cliques: sets of nodes all joined to each other, not contained in a larger such set.

Only non-trivial cliques are returned, with at least min_size nodes (3 by default: single nodes and edges are left out). Edges are taken as undirected and unweighted (in directed networks, two nodes are joined if there is an edge in either direction), self loops and parallel edges are ignored. In multilayer networks only intra-layer edges count, so cliques are within a layer (couplings would make the copies of each entity a clique).

Edges in no triangle cannot be in a clique of 3 or more nodes, so they are removed first, with the triangle enumeration of global_clustering() (on the device of the network); maximal cliques are then listed by Bron-Kerbosch with pivoting (Tomita et al., 2006) on what remains, on the CPU. The number of maximal cliques can grow exponentially with the size of dense networks.

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network.

  • component – Index of the component (0 is the largest), or None for the whole network.

  • min_size – Smallest clique returned (at least 3).

  • batch_size – Number of 2-paths expanded at once in the triangle enumeration.

Returns:

List of arrays of input node ids, one per clique, largest first.

Raises:

ValueError – If min_size is below 3.

Example:

import graphoskop as gsk

net = gsk.load_network("edges.tsv")
cliques = gsk.maximal_cliques(net)
len(cliques[0])                          # size of the largest clique
big = gsk.maximal_cliques(net, min_size = 5)

Discovery

BigCLAM

BigCLAM fits a community affiliation model, a nonnegative factorization in which every community a pair of nodes shares raises the probability of an edge between them: communities overlap, and their overlaps are denser than the rest, as in real networks.

res = gsk.bigclam_communities(net, seed = 0)                   # number of communities chosen by held-out pairs
res["groups"], res["overlapping"], res["memberships"]          # affiliation of every node to every community
gsk.bigclam_communities(net, groups = 50, attribute = "cover") # given number: much faster
graphoskop.bigclam_communities(net, attribute='community', groups=None, max_groups=100, max_iter=2000, seed=None)

BigCLAM (Yang and Leskovec, 2013): overlapping communities from a community affiliation model, the nonnegative factorization of the network that makes it most likely. Every node \(u\) has a nonnegative affiliation \(F_{uc}\) to every community \(c\); each community independently links two nodes with probability \(1 - e^{-F_{uc} F_{vc}}\), so that

\[P(u \sim v) = 1 - (1 - \epsilon) e^{-F_u \cdot F_v},\]

with a background probability \(\epsilon = 2m / (n (n - 1))\) (the density of the network) of linking any two nodes, as in the community affiliation graph model (Yang and Leskovec, 2012) that BigCLAM relaxes: the more communities two nodes share, the more likely they are linked, so overlaps of communities are denser than the communities themselves, as in real networks (unlike methods that assume overlaps are sparse). The log-likelihood

\[\ell(F) = \sum_{(u, v) \in E} \log(1 - (1 - \epsilon) e^{-F_u \cdot F_v}) + \sum_{(u, v) \notin E} [\log(1 - \epsilon) - F_u \cdot F_v]\]

is maximized over \(F \geq 0\); the sum over the non-edges is the sum over all pairs, \(\frac{1}{2} (\| \sum_u F_u \|^2 - \sum_u \|F_u\|^2)\), minus that over the edges, so every step costs \(O((m + n) K)\) (sparse products). Unlike the paper (one node at a time, on the CPU), all the affiliations move together, on the device of the network, by accelerated projected gradient ascent (FISTA, with restarts), each step scaled by the inverse curvature of the edge terms and shortened until it increases the likelihood (the node by node updates of the paper stopped at a lower likelihood in our tests), until the log-likelihood grows by less than 0.01% in 20 steps. The affiliations start from locally minimal neighborhoods, as in the paper: the neighborhoods (a node and its neighbors) of lowest conductance not beaten by those of their neighbors.

A node is in community \(c\) if \(F_{uc} \geq \delta = \sqrt{-\log(1 - \epsilon)}\), the affiliation at which a community links two nodes as likely as the background; a node in none is put in the community of its largest affiliation (a community of its own if all are 0). Communities left empty are dropped.

The number of communities groups, if not given, is chosen as in the paper, by the likelihood of held-out pairs of nodes: 20% of the edges, and as many non-adjacent pairs (standing for 20% of all the non-adjacent pairs, their likelihood weighted accordingly), are held out, the model is fitted to the rest for 10 numbers between 2 and max_groups (evenly spaced on a log scale), and the number giving the largest likelihood of the held-out pairs is fitted to the whole network. This takes 10 more fits: giving groups is much faster.

Directions, weights, parallel edges and self loops are ignored. Communities are numbered by decreasing size and written as the node attribute attribute, with a tuple of numbers for a node in several communities.

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network, not multilayer, modified in place.

  • attribute – Name of the node attribute written.

  • groups – Number of communities \(K\) of the model, or None to choose it.

  • max_groups – Largest number of communities tried when groups is None.

  • max_iter – Maximum number of gradient steps of each fit.

  • seed – Seed of the random numbers, or None.

Returns:

A dictionary with the number of groups of the model, the number of communities found (non-empty, counting the nodes without any affiliation, each alone), the number of overlapping nodes, the log_likelihood and the memberships (affiliations \(F\), a tensor of n x groups in network wide node order, columns in the order of the model, not of the community numbers).

Raises:

ValueError – If the network is multilayer, or groups or max_groups are not valid.

Example:

import graphoskop as gsk

net = gsk.load_network("edges.tsv", device = "cuda")
res = gsk.bigclam_communities(net, seed = 0)                 # number of communities chosen
res["groups"], res["overlapping"]
res = gsk.bigclam_communities(net, groups = 50, attribute = "cover")

DEMON

DEMON finds communities in the ego network of every node (its neighbors, without it), by label propagation, and merges those similar enough: since every node is in the local communities of all its neighbors, communities overlap.

res = gsk.demon_communities(net, seed = 0)                     # merge if sharing 25% of the smaller
res["communities"], res["local"], res["overlapping"]
gsk.demon_communities(net, epsilon = 0.75, min_size = 5)       # fewer merges, larger communities only
graphoskop.demon_communities(net, attribute='community', epsilon=0.25, min_size=3, weight=None, max_iter=100, seed=None)

DEMON (Coscia, Rossetti, Giannotti and Pedreschi, 2012): overlapping communities from the local point of view of every node. For every node, its ego network without it (its neighbors and the edges among them) is split into communities by label propagation (as in label_propagation_communities(), asynchronous); the node is added back to each of them, since it belongs to all the communities of its neighbors. Local communities with fewer than min_size nodes are dropped, and the others are merged into global ones: a local community merges into a global one if the nodes they share are at least a fraction epsilon of the smaller of the two.

The ego networks are independent: their label propagations run in parallel, in a compiled kernel (Numba) on the CPU. Merging is sequential, as in the original: local communities are taken in order (by ego, then label), and each joins a global community or becomes a new one. Each local community is compared only with the global communities containing some of its nodes, found in an inverted index (the communities of every node), so its cost grows with the memberships of its nodes rather than with the number of communities. When several global communities are similar enough, it joins the most similar (the original joins the first found, in an order that changes as communities merge). Merging all similar pairs at once instead, by connected components, chains communities into a few giant ones at small epsilon: the sequential merge limits chains, since a global community only grows when a new local community is close to it.

Directions are ignored and self loops dropped; parallel edges add their weights. Communities are numbered by decreasing size and written as the node attribute attribute, a tuple of numbers for a node in several; a node in none (all its communities smaller than min_size) is a community of its own.

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network, modified in place.

  • attribute – Name of the node attribute written.

  • epsilon – Smallest shared fraction of the smaller community for two communities to merge, between 0 (excluded) and 1: the smaller, the more merges (fewer, larger communities).

  • min_size – Smallest number of nodes of a community (the ego included).

  • weight – Name of the edge attribute used as edge weight in the label propagations, or None for unit weights.

  • max_iter – Maximum number of sweeps of each label propagation.

  • seed – Seed of the random numbers, or None.

Returns:

A dictionary with the number of communities (of at least min_size nodes), the number of local communities of at least min_size nodes found in the ego networks (before merging), and the number of overlapping nodes.

Raises:

ValueError – If epsilon is not in \((0, 1]\), min_size is below 1, or weights are negative.

Example:

import graphoskop as gsk

net = gsk.load_network("edges.tsv")
res = gsk.demon_communities(net, seed = 0)
res["communities"], res["overlapping"]
gsk.demon_communities(net, epsilon = 0.5, min_size = 5, attribute = "demon")   # fewer merges

Hierarchical random graphs

Hierarchical random graphs, also used to predict links (Link prediction), give a hierarchy of groups: the consensus of the dendrograms sampled in proportion to their likelihood, from the groups of nodes found in most of them. The groups can be communities or disassortative sets.

res = gsk.hierarchical_random_graph_communities(net, seed = 0)   # community, community_1, ...: top level first
res["groups"], res["communities"], res["log_likelihood"]
gsk.hierarchical_random_graph_communities(net, burnin = 50000, consensus = 0.9)   # longer chains, surer groups
graphoskop.hierarchical_random_graph_communities(net, attribute='community', samples=100, burnin=20000, interval=10, consensus=0.5, chains=None, seed=None)

Hierarchical communities from hierarchical random graphs (Clauset, Moore and Newman, 2008): the consensus of the dendrograms sampled in proportion to their likelihood, as in hierarchical_random_graph_lp().

A hierarchical random graph is a dendrogram whose leaves are the nodes, with a probability \(p_r\) of connection between the leaves whose lowest common ancestor is the internal node \(r\). Every internal node is a group of nodes (its leaves). The dendrograms are sampled by Markov chain Monte Carlo (burnin sweeps of \(n\) moves per chain, then a sample every interval sweeps, samples in all, from chains running in parallel), and the groups found in more than a fraction consensus of the samples form the majority consensus tree: with consensus at least 0.5 the groups are nested or disjoint, so they form a tree, in which an internal node can have more than two children, and nodes whose place in the hierarchy is uncertain hang from the lowest group that is certain. Groups can be communities (dense inside) or sets of nodes linked mostly to the rest (as the two types of a bipartite network): the model learns both.

The levels of the consensus tree are written as numeric node attributes, top first: attribute for the children of the root, attribute + "_1", attribute + "_2", … for the levels below, each refining the one above (in branches that stop earlier, nodes keep their deepest group; a node hanging from the root is a group of its own). Groups are numbered by decreasing size at every level.

The model is undirected and unweighted: directions, weights, parallel edges and self loops are ignored; isolated nodes are leaves too. The chains are those of hierarchical_random_graph_lp(), but the consensus needs them to have converged more than the edge probabilities do: a group is kept only if the chains agree on it, so chains still climbing towards different dendrograms leave most nodes hanging from the root. Hence the larger default burnin: on a benchmark of 1,000 nodes, 5,000 sweeps found 3 groups, 20,000 sweeps 30 (normalized mutual information with the planted communities 0.58 and 0.88). Larger networks need more; if the top level has mostly single nodes, raise burnin. The samples are kept in memory (about 30 bytes per node and sample).

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network, not multilayer, modified in place.

  • attribute – Name of the node attribute of the top level.

  • samples – Number of sampled dendrograms.

  • burnin – Number of sweeps of each chain before its first sample.

  • interval – Number of sweeps between samples.

  • consensus – A group is kept if found in more than this fraction of the samples, between 0.5 and 1.

  • chains – Number of chains, None for the number of Numba threads.

  • seed – Seed of the random numbers, or None.

Returns:

A dictionary with the mean log_likelihood of the sampled dendrograms, the number of groups of the consensus tree (its internal nodes, the root excluded) and communities, the number of groups of every level, top first.

Raises:

ValueError – If the network is multilayer, or samples, burnin, interval or consensus are not valid.

Example:

import graphoskop as gsk

net = gsk.load_network("edges.tsv")
res = gsk.hierarchical_random_graph_communities(net, seed = 0)    # community, community_1, ...
res["communities"]
gsk.hierarchical_random_graph_communities(net, burnin = 20000, consensus = 0.9, attribute = "sure")

Infomap

Infomap finds the modules in which a random walker stays the longest, by the map equation: hierarchically, following edge directions, and across the layers of multilayer networks; or overlapping modules, with nodes coded in several of them.

res = gsk.infomap_communities(net, seed = 0)                   # community, community_1, ...: top level first
res["codelength"], res["codelength_one_module"], res["modules"]
res = gsk.infomap_communities(net, hierarchical = False, trials = 10, seed = 0)   # two levels, best of 10
res = gsk.infomap_communities(citations, teleportation = 0.15)  # walker following edge directions
res = gsk.infomap_communities(net, max_communities = 2, attribute = "cover")   # overlapping modules
gsk.codelength(net, "cover")                                   # overlapping map equation
graphoskop.infomap_communities(net, attribute='community', weight=None, directed=None, hierarchical=True, teleportation=0.15, max_communities=1, trials=1, sweeps=50, seed=None, physical=None)

Infomap (Rosvall and Bergstrom, 2008): the modules that compress the description of a random walk on the network the most, by the map equation. The walker’s steps are described with one codeword per node, unique within its module, plus codewords to enter and exit modules: when the walker stays long in modules, short codewords reused across modules pay off. The map equation is the average length of the description of a step, in bits; for a two-level partition into modules \(i\),

\[L = q \, H(\mathcal{Q}) + \sum_i p_i^{\circlearrowright} H(\mathcal{P}^i),\]

with \(q = \sum_i q_i^{in}\) the rate of entering modules, \(H(\mathcal{Q})\) the entropy of the module entry rates, \(p_i^{\circlearrowright} = q_i^{out} + \sum_{\alpha \in i} p_\alpha\) the rate of use of module \(i\)’s codebook, and \(H(\mathcal{P}^i)\) the entropy of its exit rate and of the visit rates of its nodes.

  • Hierarchy (hierarchical = True; Rosvall and Bergstrom, 2011): modules can have submodules, each with its own codebook holding its exit and the entries of its submodules, at any depth, and depths can differ across branches. Every module is split recursively while a two-level partition of it, its index codebook also holding its exit, is shorter than its own codebook; then modules are grouped into super-modules while this shortens the top codebook.

  • Directions (directed, by default as the network): the walker follows edge directions, teleporting with probability teleportation (and always from nodes without out-edges) to the start of a random edge, so that the network needs no strong connectivity; as in the Infomap software, teleportation steps are not coded (unrecorded teleportation: Lambiotte and Rosvall, 2012), so only the flow along edges defines the modules. Undirected networks, or directed = False, give a walker that steps along an edge with probability proportional to its weight, with visit rates proportional to the node strengths.

  • Layers (multilayer networks; De Domenico et al., 2015): the walker moves on the supra-graph, changing layer along couplings and interlayer edges in proportion to their weights, and every copy (entity, layer) has its own module, but the copies of an entity in the same module share one codeword (the physical node), so that entities active in several layers are not penalized for being in a module through several of them.

  • Memory (physical; Rosvall et al., 2014): the nodes are states of a walker with memory (memory_network(), higher_order_dependency_network()), and the node attribute physical gives the place of each ("first_order_node"). As for layers, the states of a place in the same module share its codeword, and a place belongs to every module of its states: overlapping modules of places, found without the overlapping search.

The map equation is minimized as in the Infomap software: greedy moves of nodes between modules, in random order, then the modules found move as nodes and merge while it shortens the codelength (as in the Louvain method), then fine tuning (the nodes move again from the modules found), repeated while the codelength decreases. The moves run in compiled kernels (Numba) on the CPU; the result is a heuristic optimum, possibly different across seeds: trials runs keep the shortest. Self loops are ignored; parallel edges add their weights; nodes without edges are never visited and are modules of their own. Unlike the Infomap software, modules are not moved by their submodules (coarse tuning), so codelengths can be slightly longer on hard networks.

Overlapping modules (max_communities above 1; Esquivel and Rosvall, 2011): a node can be in several modules, with a codeword in each. The walker stays in its module when it steps to a node of the module; otherwise it exits it and enters one of the modules of the new node, chosen uniformly; the visit rates of the node are thus split among its modules, as the rates of being there in each. A node in two modules saves the exits and entries of the walker passing through it between them, at the cost of two codewords. From the two-level partition (hierarchical is not used), the change of codelength of every node joining one more module of a neighbor is computed (with the other visit rates fixed; exact while the neighbors are in one module), the best per node are sorted, and the best \(k\) of them are applied together, \(k\) chosen by the exact codelength (stationary visit rates of all the states, by power iteration) on a doubling grid refined around its best point (Esquivel and Rosvall fit parabolas instead), repeated while the codelength decreases. A node is in at most max_communities modules. Not for multilayer networks.

Modules are numbered by decreasing flow (0 is the module most visited by the walker) and written as numeric node attributes: attribute for the top level (the modules of a two-level partition with hierarchical = False) and attribute + "_1", attribute + "_2", … for the levels below, each refining the one above (in branches that stop earlier, nodes keep their deepest module).

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network, modified in place.

  • attribute – Name of the node attribute of the top level of modules.

  • weight – Name of the edge attribute used as edge weight, or None for unit weights.

  • directed – Whether the walker follows edge directions; None for the directions of the network.

  • hierarchical – Whether to search modules within modules (and super-modules).

  • teleportation – Probability of teleporting at each step, in directed networks.

  • max_communities – Maximum number of modules of a node; above 1 for overlapping modules, written as one attribute (a node in several modules has a tuple of numbers, by decreasing size).

  • trials – Number of independent runs of the two-level search, keeping the shortest.

  • sweeps – Maximum number of sweeps of node moves in each round.

  • seed – Seed of the random numbers, or None.

  • physical – Name of the node attribute giving the physical node of every node (states of a network with memory), or None (in multilayer networks, the entities).

Returns:

A dictionary with the codelength (bits per step of the walker) of the whole hierarchy, the same as codelength() of the list of all the levels ([attribute, attribute + "_1", ...]; a single level alone is scored as a two-level partition, with a longer codelength, since it lacks the codebooks of the other levels), the codelength_one_module (all nodes in one module: the entropy of the visit rates; the compression is the difference), and modules, the number of modules of every level, top first; with overlaps, the codelength is that of the overlapping modules and the number of overlapping nodes is added.

Raises:

ValueError – If weights are negative, directed is True for an undirected network, teleportation is not between 0 and 1, or max_communities is not a positive integer (or above 1 in a multilayer network or with physical), or physical has missing values.

Example:

import graphoskop as gsk

net = gsk.load_network("edges.tsv", directed = True)
res = gsk.infomap_communities(net, seed = 0)               # community, community_1, ...
res["modules"], res["codelength"]
res = gsk.infomap_communities(net, hierarchical = False, directed = False, trials = 10)
res = gsk.infomap_communities(net, max_communities = 2, attribute = "cover")   # overlapping
mem = gsk.memory_network("paths.txt")                      # states "k|j": at k, from j
gsk.infomap_communities(mem, weight = "weight", physical = "first_order_node")

Label propagation

Nodes repeatedly take the label most common among their neighbors, until labels settle; updating the nodes by colors (or one at a time) keeps the two sides of bipartite structures from swapping labels forever. With several labels per node (COPRA), communities overlap.

gsk.label_propagation_communities(net, seed = 0)                               # by colors, on the device
gsk.label_propagation_communities(net, strategy = "asynchronous", weight = "weight", seed = 0)
gsk.label_propagation_communities(net, max_communities = 3, attribute = "cover")   # overlapping
graphoskop.label_propagation_communities(net, attribute='community', weight=None, strategy='semisynchronous', max_communities=1, max_iter=100, seed=None)

Label propagation (Raghavan, Albert and Kumara, 2007): every node starts with its own label and repeatedly takes the label carried by most of its neighbors (by total edge weight), until every node has a label of largest weight among its neighbors; the groups of nodes sharing a label are the communities. A node keeps its label when it is one of the most frequent (ties among the others are broken at random), so that the process stops.

How the labels are updated matters. If all nodes change at once (synchronous updates), the two sides of a bipartite network (or any two sets of nodes linked mostly between them) can swap their labels at every step, forever. Two strategies avoid it:

  • "semisynchronous" (Cordasco and Gargano, 2010): the nodes are colored (greedily, so that neighbors have different colors), and the nodes of one color update at once, color after color: neighbors never change together, the process always converges, and every step runs on the device of the network, for all the nodes of a color in parallel;

  • "asynchronous" (the original): the nodes update one at a time, in a new random order at every sweep, each seeing the labels already changed in the sweep; it runs in a compiled kernel (Numba) on the CPU.

Directions are ignored, self loops do not vote and parallel edges add their weights. Nodes without edges are communities of their own. The result depends on the random order and ties: different seeds can give different communities.

Overlapping communities (max_communities above 1) follow COPRA (Gregory, 2010): every node holds up to max_communities labels, each with a belonging coefficient, the coefficients summing to 1 (at the start, its own label with coefficient 1). A node takes the labels of its neighbors with the mean of their coefficients, weighted by the edge weights, drops the labels below 1 / max_communities (keeping the largest, ties at random, if all are below) and normalizes the coefficients of the others; the process stops when a sweep changes no set of labels or, as in COPRA, when the labels in use stay the same and none of them is held by fewer nodes than before (a few nodes can keep switching labels). Then, as in COPRA, a community contained in another one is removed. A node joins several communities only if they all carry at least 1 / max_communities of its neighborhood: max_communities = 2 needs an almost exact tie, so 3 or more is more useful. Both strategies apply (Gregory updates all nodes at once, which can oscillate as above); both run in a compiled kernel on the CPU. max_communities = 1 is the classic label propagation.

Communities are numbered by decreasing size and written as the numeric node attribute attribute; with max_communities above 1, a node in several communities has a tuple of numbers.

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network, modified in place.

  • attribute – Name of the node attribute written.

  • weight – Name of the edge attribute used as edge weight, or None for unit weights.

  • strategy – "semisynchronous" or "asynchronous".

  • max_communities – Maximum number of communities of a node (COPRA’s \(v\)).

  • max_iter – Maximum number of sweeps over all the nodes; a warning is raised if they end before convergence.

  • seed – Seed of the random numbers, or None.

Returns:

A dictionary with the number of communities, the number of iterations (sweeps over all the nodes) and whether the labels converged; with max_communities above 1, also the number of overlapping nodes (in several communities).

Raises:

ValueError – If strategy or max_communities are not valid, or weights are negative.

Example:

Leiden

The Leiden algorithm maximizes modularity (in the variant of the network: directed, bipartite, multilayer) or the constant Potts model, refining the communities at every level so that they are always connected.

res = gsk.leiden_communities(net, seed = 0)                    # maximum modularity
res["quality"], res["communities"]
gsk.leiden_communities(net, resolution = 2, attribute = "small")              # smaller communities
gsk.leiden_communities(net, quality = "cpm", resolution = 0.05)               # internal density >= 0.05
gsk.leiden_communities(net, initial = "community", attribute = "improved")    # from a partition
graphoskop.leiden_communities(net, attribute='community', weight=None, quality='modularity', resolution=1, randomness=0.01, initial=None, max_iter=100, seed=None)

Leiden algorithm (Traag, Waltman and van Eck, 2019): communities of high quality, every one of them guaranteed to be connected. Like the Louvain method, nodes move greedily to the community that improves the quality the most and the communities found become the nodes of a smaller network, at every level; but Louvain can leave communities internally disconnected (a node that held them together moves away), which Leiden avoids with a refinement step. Every level has three phases:

  • fast local moving: nodes are taken from a queue (all of them at first, in random order) and moved to the best community; when a node moves, its neighbors outside its new community join the queue again, so that only the nodes affected by changes are visited;

  • refinement: every community is split into the singletons of its nodes, which then merge, in random order, only with clusters of the same community, only if both are well connected to the rest of the community, and choosing at random among the merges that do not decrease the quality, with probability proportional to \(\exp(\Delta H / \theta)\) (randomness \(\theta\), with \(\Delta H\) in units of edge weight as in the paper; the smaller, the greedier), which explores the space of partitions better;

  • aggregation: the refined clusters become the nodes of the next level, starting in the communities found by the local moving (a community can thus be split at the next level).

The levels end when every community is a single node; the whole algorithm then starts again from the partition found, until it does not improve (at most max_iter times).

quality is the function maximized:

  • "modularity": the modularity of modularity(), in the variant of the network (directed, bipartite and multilayer), with resolution \(\gamma\);

  • "cpm": the constant Potts model (Traag, Van Dooren and Nesterov, 2011), \(H = \sum_c \left[ E_c - \gamma \binom{n_c}{2} \right]\), with \(E_c\) the weight of the edges within community \(c\) and \(n_c\) its number of nodes (ordered pairs \(n_c (n_c - 1)\) in directed networks; pairs of nodes of different types in bipartite networks; pairs in the same layer in multilayer networks): communities have internal density at least \(\gamma\) and density between them is below \(\gamma\). Unlike modularity, it has no resolution limit: \(\gamma\) sets the density of the communities whatever the size of the network.

Self loops count inside their node’s community, parallel edges add their weights. Nodes without edges are communities of their own. The moves run in compiled kernels (Numba) on the CPU; the result is a heuristic optimum that can differ across seeds.

Communities are numbered by decreasing size and written as the numeric node attribute attribute.

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network, modified in place.

  • attribute – Name of the node attribute written.

  • weight – Name of the edge attribute used as edge weight, or None for unit weights.

  • quality – "modularity" or "cpm".

  • resolution – Resolution \(\gamma\): above 1 (modularity), or larger (CPM), gives smaller communities.

  • randomness – Randomness \(\theta\) of the refinement, positive (0.01 as in the paper).

  • initial – Partition to start from (node attribute name, dictionary or Series by node id, or sequence in network wide node order, as for modularity()), or None for singletons.

  • max_iter – Maximum number of runs of the algorithm, each starting from the result of the previous one.

  • seed – Seed of the random numbers, or None.

Returns:

A dictionary with the quality of the communities found (modularity, or \(H\)), the number of communities and the number of iterations (runs of the algorithm).

Raises:

ValueError – If quality is not valid, weights are negative, randomness is not positive, or a node has no community or several in initial.

Example:

import graphoskop as gsk

net = gsk.load_network("edges.tsv")
gsk.leiden_communities(net, seed = 0)                          # maximum modularity
gsk.leiden_communities(net, resolution = 2, attribute = "small")
gsk.leiden_communities(net, quality = "cpm", resolution = 0.05)  # density at least 0.05

Link communities

Link communities group the links of the network rather than its nodes; a node is then in the communities of all its links, so communities overlap. They are found by hierarchical clustering of the links, cut at the largest partition density, or by partitioning the line graph (whose nodes are the links) by modularity. Both write the community of every edge as an edge attribute and the communities of every node as a node attribute.

res = gsk.hierarchical_link_communities(net)                   # Ahn, Bagrow and Lehmann
res["communities"], res["partition_density"], res["threshold"]
gsk.hierarchical_link_communities(net, weight = "weight", threshold = 0.3)   # cut at a similarity
res = gsk.line_graph_communities(net, seed = 0)                # Evans and Lambiotte, random walk line graph
net.get_edge_attribute("link_community", None)                 # community of every edge
graphoskop.hierarchical_link_communities(net, attribute='link_community', weight=None, threshold=None)

Link communities by hierarchical link clustering (Ahn, Bagrow and Lehmann, 2010): the links, rather than the nodes, are grouped, so that a node is in the communities of all its links and communities overlap naturally (a node can be in many), at every scale.

Two links sharing a node \(k\), \((i, k)\) and \((j, k)\), are as similar as the neighborhoods of \(i\) and \(j\), nodes included: the Jaccard coefficient \(S = |N^+(i) \cap N^+(j)| / |N^+(i) \cup N^+(j)|\); with weight, the Tanimoto coefficient \(S = a_i \cdot a_j / (|a_i|^2 + |a_j|^2 - a_i \cdot a_j)\) of the vectors of weights \(a_{ij} = w_{ij}\), with \(a_{ii}\) the mean weight of the links of \(i\). Links are merged by single linkage, by decreasing similarity, building a dendrogram of links, which is cut where the partition density

\[D = \frac{2}{M} \sum_c m_c \frac{m_c - (n_c - 1)}{(n_c - 2)(n_c - 1)}\]

is largest (\(M\) links in all, \(m_c\) links and \(n_c\) nodes in community \(c\); a community of one link counts 0): the density of every community beyond that of a tree on its nodes, weighted by its links. Or it is cut at a given similarity threshold.

The pairs of links sharing a node are \(\sum_k \binom{k_k}{2}\), so the time grows with the squares of the degrees; the clustering runs in a compiled kernel (Numba) on the CPU, keeping the nodes of every cluster to update the partition density at every merge.

Directions are ignored, parallel edges are one link (weights summed), self loops are in no community. The link communities, numbered by decreasing number of nodes, are written as the numeric edge attribute attribute (both stored directions of an edge, and its parallel copies, get the community of the link; self loops NaN), and the communities of the nodes as the node attribute attribute: a node in several has a tuple of numbers; a node without links is a community of its own.

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network, not multilayer, modified in place.

  • attribute – Name of the edge and node attributes written.

  • weight – Name of the edge attribute used as edge weight, or None for unit weights.

  • threshold – Similarity at which the dendrogram is cut, or None for the largest partition density.

Returns:

A dictionary with the number of link communities, the partition_density of the cut, the similarity threshold of the cut (infinite if no merge increases the partition density: every link alone), and the number of overlapping nodes (in several communities).

Raises:

ValueError – If the network is multilayer or weights are negative.

Example:

import graphoskop as gsk

net = gsk.load_network("edges.tsv")
res = gsk.hierarchical_link_communities(net)                 # link_community, edges and nodes
res["communities"], res["partition_density"]
gsk.hierarchical_link_communities(net, threshold = 0.3, attribute = "links")
graphoskop.line_graph_communities(net, attribute='link_community', weight=None, line_graph='random_walk', resolution=1, seed=None)

Link communities from the line graph (Evans and Lambiotte, 2009, 2010): the communities of the line graph, whose nodes are the links of the network, two of them adjacent if they share a node, are communities of links, so that a node is in the communities of all its links and communities overlap. The line graph is partitioned by maximizing its modularity with the Leiden algorithm (leiden_communities(), at resolution). Its edge weights, for links \(\alpha\) and \(\beta\) sharing the node \(i\), follow line_graph:

  • "plain": 1 (the line graph \(C\)). A node of degree \(k\) becomes a clique of \(\binom{k}{2}\) edges, so that high degree nodes dominate;

  • "weighted": \(1 / (k_i - 1)\) (the line graph \(D\)), so that the pairs of links of a node weigh \(k_i / 2\) in all, in proportion to its degree as in the network;

  • "random_walk": \(w_\alpha w_\beta / s_i\) with self loops \(\sum_{i \in \alpha} w_\alpha^2 / s_i\) (the line graph \(E\), with the strength \(s_i\) of node \(i\); \(1 / k_i\) without weights): the flow of a random walker moving from link to link through their shared nodes, in proportion to the link weights (the only variant using weight; Evans and Lambiotte, 2010). Its modularity is that of a partition of the links of the original network with a null model of walkers on links.

The line graph has \(\sum_i \binom{k_i}{2}\) edges, so memory grows with the squares of the degrees.

Directions are ignored, parallel edges are one link (weights summed), self loops are in no community. Link communities are written as for hierarchical_link_communities(): the numeric edge attribute attribute and the node cover attribute.

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network, not multilayer, modified in place.

  • attribute – Name of the edge and node attributes written.

  • weight – Name of the edge attribute used as edge weight ("random_walk" only), or None for unit weights.

  • line_graph – "random_walk", "weighted" or "plain".

  • resolution – Resolution of the modularity of the line graph.

  • seed – Seed of the random numbers, or None.

Returns:

A dictionary with the number of link communities, the modularity of the partition of the line graph, and the number of overlapping nodes (in several communities).

Raises:

ValueError – If the network is multilayer, line_graph is not valid, weights are negative, or weight is given with another line graph than "random_walk".

Example:

import graphoskop as gsk

res = gsk.line_graph_communities(net, seed = 0)              # link_community, edges and nodes
gsk.line_graph_communities(net, line_graph = "weighted", attribute = "links")

OSLOM

OSLOM keeps only the clusters that are statistically significant, compared with random networks with the same degrees, through the order statistics of how strongly external nodes are linked to them: clusters can overlap, and nodes significantly linked to no cluster are homeless.

res = gsk.oslom_communities(net, seed = 0)
res["communities"], res["homeless"], res["overlapping"]
gsk.oslom_communities(net, tolerance = 0.5, iterations = 2, attribute = "oslom")   # looser, faster
graphoskop.oslom_communities(net, attribute='community', tolerance=0.1, iterations=10, runs=10, union=0.7, seed=None)

OSLOM (Lancichinetti, Radicchi, Ramasco and Fortunato, 2011): overlapping communities that are statistically significant, by the order statistics of a local fitness score. Nodes not significantly linked to any community are left out of all (homeless).

Significance. For a node \(i\) outside a cluster \(C\), with \(k_i\) links of which \(k_i^{in}\) to \(C\), the probability of having at least \(k_i^{in}\) links to \(C\) in the configuration model (the hypergeometric approximation of the paper: \(k_i\) stubs drawn among those not inside \(C\), of which \(m_C^{out}\) leave \(C\)) gives its r-score, drawn uniformly between the probabilities of more than and of at least \(k_i^{in}\) links (a random tie break of the discrete distribution). Under the null model the r-scores of the \(N - n_C\) external nodes are uniform, so the \(q\)-th smallest has the distribution \(\Omega_q(r) = P(\mathrm{Bin}(N - n_C, r) \geq q)\); the \(q\) best nodes are significantly linked to \(C\) if \(\phi(\Omega_q(r_q)) < P\) (tolerance), with \(\phi\) the distribution of \(\min_q \Omega_q(r_q)\) under the null model (the correction for looking at the best \(q\); simulated once, for \(q\) up to 200).

Single cluster analysis. External nodes are added while significant (for the first \(q\), from 1 up, with \(\phi(\Omega_q(r_q)) < P\): the best node alone, or else the best two together, and so on), then the internal node with the worst r-score (as an external node of the rest) is removed while not significant, alternately until nothing changes. Since the scores are random, the analysis is repeated runs times (the paper uses 100): the cluster is significant if more than half the outcomes are non-empty, and keeps the nodes in more than half of them.

Cover. As in the OSLOM software, which explores the network with a Louvain-like method, the candidate clusters are the communities of the Leiden algorithm (leiden_communities(), a different seed in each of the iterations), each going through the single cluster analysis: it can lose nodes, and gain nodes of other clusters (the overlaps). (Growing clusters from single random nodes, as also described in the paper, let clusters reaching nodes shared with another community absorb that community too.) A cluster must be minimal: its own subnetwork is explored the same way, and if two or more significant subclusters cover more than union of it (the paper’s \(P_2 = 0.7\)), they replace it. Then clusters sharing more than half of the smaller one are resolved, most overlapping first: they merge unless their union has significant subclusters covering more than union of it, in which case the larger is kept. Not implemented: the hierarchical levels (clusters of clusters) and weighted or directed networks (directions are ignored, weights not used).

The single cluster analyses run in a compiled kernel (Numba) on the CPU; the result depends on the seed. Communities are numbered by decreasing size and written as the node attribute attribute, a tuple of numbers for a node in several; a homeless node is a community of its own.

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network, modified in place.

  • attribute – Name of the node attribute written.

  • tolerance – Significance threshold \(P\): larger keeps more and larger clusters.

  • iterations – Number of runs of the Leiden algorithm giving candidate clusters.

  • runs – Number of repetitions of every single cluster analysis.

  • union – Fraction of a cluster that significant subclusters must cover to replace it.

  • seed – Seed of the random numbers, or None.

Returns:

A dictionary with the number of significant communities, the number of homeless nodes and the number of overlapping nodes.

Raises:

ValueError – If tolerance or union are not in \((0, 1)\), or iterations or runs are below 1.

Example:

import graphoskop as gsk

net = gsk.load_network("edges.tsv")
res = gsk.oslom_communities(net, seed = 0)
res["communities"], res["homeless"], res["overlapping"]
gsk.oslom_communities(net, tolerance = 0.5, runs = 100, attribute = "oslom")

Stochastic blockmodels

Every stochastic blockmodel of the generators (see Generators) finds communities when fitted to a network: the groups under which the network is most likely. Models with more structure describe more kinds of groups, at a higher cost in description length.

fit = gsk.block_model_communities(net, seed = 0)                                  # nested, degree-corrected
fit = gsk.block_model_communities(net, gsk.degree_corrected_block_model, seed = 0)
fit = gsk.block_model_communities(net, "stochastic_block_model", groups = 4, seed = 0)
fit = gsk.block_model_communities(net, "planted_partition_graph", seed = 0)
fit = gsk.block_model_communities(net, "mixed_membership_block_model", groups = 3, attribute = "cover", seed = 0)
gsk.modularity(net, "cover")                                                      # overlapping modularity
graphoskop.block_model_communities(net, model='nested_block_model', groups=None, attribute='community', threshold=None, max_blocks=4096, sweeps=10, max_iter=500, seed=None)

Communities from the stochastic blockmodels of the generators (see Generators): the partition, the hierarchy of partitions or the overlapping memberships under which the network is most likely, given the generator of the model as model (the function or its name).

  • nested_block_model() (default), degree_corrected_block_model(), stochastic_block_model(), planted_partition_graph(): the partition minimizing the description length of Peixoto’s nonparametric microcanonical version of each model, as in fit_nested_block_model() (which this generalizes; see it for the description length and the agglomerative heuristic). The description length counts the cost of the groups too, so the number of groups is chosen by the model, unless groups fixes it (for the nested model, the groups of the bottom level). The degree-corrected models expect groups of nodes with any degrees; the others, nodes of similar degrees in each group (with broad degrees they tend to group hubs together); the planted partition has one density inside all groups and one between them (higher inside for communities, lower for bipartite-like structures).

  • mixed_membership_block_model(): overlapping communities. Every node has weights \(\pi_i\) over groups blocks (by default, the number of groups of the stochastic blockmodel fitted first, which tends to be larger than the number of blocks, as nodes mixing blocks in different proportions form groups of their own: give groups when it is known), and \(\pi_i^T B \pi_j\) edges are expected between nodes \(i\) and \(j\). The memberships and the block matrix \(B\) maximize the likelihood of the edges (Poisson, the limit of the Bernoulli likelihood for sparse networks), computed in \(O((m + n) K^2)\) without going through all pairs of nodes, by L-BFGS on the device of the network (up to max_iter iterations), starting from the partition of the stochastic blockmodel with groups groups. This is a local maximum: the likelihood is not concave.

The groups are written as node attributes: for the partitions, the numeric node attribute attribute (groups numbered from 0), and for the nested model also attribute + "_1", attribute + "_2", … for the levels above; for the mixed memberships, the qualitative node attribute attribute with the blocks of weight at least threshold of every node (a tuple of blocks, or the block for a node in one; see Several values per node: overlapping communities), as in the generator. The partitions are fitted by compiled kernels on the CPU (see Network error correction), on undirected networks (parallel edges count once, self loops are ignored); the mixed memberships also on directed ones.

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network, not multilayer, modified in place; undirected, except for the mixed membership model.

  • model – Generator of the model, or its name.

  • groups – Number of groups (of the bottom level for the nested model; of blocks for the mixed membership model), or None to let the description length choose it.

  • attribute – Name of the node attribute written.

  • threshold – Mixed membership model: smallest weight of a block for a node to be listed in it; None for 1 / (groups + 1).

  • max_blocks – Maximum number of groups of the bottom level.

  • sweeps – Maximum number of greedy sweeps after each merge round.

  • max_iter – Mixed membership model: maximum number of L-BFGS iterations.

  • seed – Seed of the random numbers, or None.

Returns:

A dictionary with model (the generator name) and groups (the number of groups of every level, bottom first, for the partitions; the number of blocks for the mixed memberships); for the partitions, description_length; for the mixed memberships, log_likelihood, memberships (the \(n\) by groups float64 tensor of the weights of every node, in the network wide node order, on the device of the network) and probs (the matrix \(B\), expected edges between nodes fully in each pair of blocks).

Raises:

ValueError – If model is not one of these generators, the network is multilayer or, except for the mixed membership model, directed, or groups is not between 1 and the number of nodes (and max_blocks).

Example:

import graphoskop as gsk

net = gsk.load_network("edges.tsv")

fit = gsk.block_model_communities(net, gsk.degree_corrected_block_model, seed = 0)

Quality of a partition

Modularity compares the edges within communities with those expected at random; the codelength of the map equation measures how well communities trap a random walker, in bits per step (normalized, relative to no communities, to compare networks of different sizes). Conductance, internal density and out-degree fraction score every community by its edges (inside it, or leaving it), either one community or all of them (their mean, or a pandas.Series by community); they accept overlapping communities.

gsk.modularity(net, "community")
gsk.codelength(net, "community")                         # bits per step of the walker
gsk.codelength(net, "community", normalized = True)      # below 1: the communities compress the walk
gsk.codelength(net, ["module", "module_1"])              # a hierarchy, top level first (as returned by Infomap)
gsk.conductance(net, "community")                        # mean over the communities
gsk.conductance(net, "community", community = 3)         # one community
gsk.internal_density(net, "community", aggregate = "size")       # mean weighted by community size
gsk.out_degree_fraction(net, "community", kind = "flake", aggregate = None)   # Series by community
graphoskop.codelength(net, partition, weight=None, directed=None, teleportation=0.15, normalized=False, physical=None)

Codelength of a partition by the map equation (see infomap_communities()): the average number of bits per step needed to describe a random walk on the network with the modules of the partition. The shorter, the better the modules trap the walker, so it measures the quality of any partition (from any method), as modularity() does from a different point of view.

The walk is that of infomap_communities(), with the same weight, directed and teleportation, and in multilayer networks the copies of an entity in the same module share a codeword (as do the nodes of the same physical node). A hierarchy of modules is given as a list of node attribute names, top level first, each level refining the one above (as written by infomap_communities()); its codelength is that of the hierarchical map equation. A single level is always scored as a two-level partition: to compare with the codelength returned by infomap_communities(), give all its levels. Overlapping communities (a node with several labels) are scored by the overlapping map equation of Esquivel and Rosvall (2011), as found by infomap_communities() with max_communities above 1 (not in multilayer networks, nor as a hierarchy).

With normalized, the codelength is divided by that of a single module (no communities: the entropy of the visit rates of the nodes, which grows with the number of nodes), so that networks of different sizes can be compared: below 1 when the partition compresses the walk, above 1 when it makes its description longer.

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network.

  • partition – Node attribute name, dictionary or pandas.Series by node id, or sequence in network wide node order, as for modularity() (one community per node); or a list of node attribute names, top level first, for a hierarchy.

  • weight – Name of the edge attribute used as edge weight, or None for unit weights.

  • directed – Whether the walker follows edge directions; None for the directions of the network.

  • teleportation – Probability of teleporting at each step, in directed networks.

  • normalized – Whether to divide by the codelength of a single module.

  • physical – Name of the node attribute giving the physical node of every node, whose nodes in the same module share a codeword (see infomap_communities()), or None.

Returns:

The codelength in bits (or its ratio to that of a single module); NaN normalized for a network without edges.

Raises:

ValueError – If a node has no community, a hierarchy has overlapping communities, or as infomap_communities().

Example:

import graphoskop as gsk

gsk.codelength(net, "party")                                   # bits per step
gsk.codelength(net, "party", normalized = True)                # comparable across networks
gsk.infomap_communities(net, attribute = "module")
gsk.codelength(net, ["module", "module_1"])                    # hierarchical map equation
graphoskop.conductance(net, partition, community=None, weight=None, aggregate='mean', component=None)

Conductance of communities: the weight of the edges leaving a community (its cut) over the smaller of its volume (sum of the degrees of its nodes) and the volume of the rest of the network,

\[\phi(S) = \frac{\mathrm{cut}(S)}{\min(\mathrm{vol}(S), \mathrm{vol}(V \setminus S))}.\]

It is between 0 (no edge leaves the community) and 1; the lower, the better separated the community. Directions are ignored and self loops dropped; parallel edges add their weights. In a cover (overlapping communities) every community is the set of its nodes. NaN for a community whose volume, or that of the rest, is 0.

  • net – A Network.

  • partition – The communities, as for modularity() (a cover is allowed).

  • community – Label of a community, to get its conductance only.

  • weight – Name of the edge attribute used as edge weight, or None for unit weights.

  • aggregate – Overall value, without community: "mean" over the communities, "size" for their mean weighted by number of nodes, or None for a pandas.Series with the value of every community (by label). NaN values are skipped.

  • component – Index of the component (0 is the largest), or None for the whole network.

Returns:

A float, or a pandas.Series.

Raises:

  • KeyError – If there is no such community or attribute.

  • ValueError – If aggregate is not valid, or as modularity().

gsk.conductance(net, "party", aggregate = None)     # every party
graphoskop.internal_density(net, partition, community=None, weight=None, aggregate='mean', component=None)

Internal density of communities: the weight of the edges within a community over the number of pairs of its nodes that could be connected, \(\frac{2 E_S}{n_S (n_S - 1)}\) in undirected networks (\(\frac{E_S}{n_S (n_S - 1)}\) in directed ones, where \(E_S\) counts the edges in both directions; \(\frac{E_S}{n^{(0)}_S n^{(1)}_S}\) in bipartite ones, pairs of nodes of different types). Multilayer networks are taken as their supra-graph: copies are nodes, and couplings and interlayer edges are edges. With unit weights it is between 0 and 1 (1 for a clique). Self loops are dropped; parallel edges add their weights. NaN for a community without pairs (a single node).

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network.

  • partition – The communities, as for modularity() (a cover is allowed).

  • community – Label of a community, to get its density only.

  • weight – Name of the edge attribute used as edge weight, or None for unit weights.

  • aggregate – Overall value, without community, as for conductance().

  • component – Index of the component (0 is the largest), or None for the whole network.

Returns:

A float, or a pandas.Series.

Raises:

  • KeyError – If there is no such community or attribute.

  • ValueError – If aggregate is not valid, or as modularity().

Example:

gsk.internal_density(net, "party")                  # mean over the parties
gsk.internal_density(net, "party", aggregate = "size")
graphoskop.modularity(net, partition, weight=None, resolution=1, component=None, overlap='shen')

Modularity of a partition of the nodes into communities: the weight of the edges within communities minus its expected value in a null model that keeps the degrees.

The variant follows the kind of network:

  • undirected (Newman, 2006): \(Q = \sum_c \left[ \frac{L_c}{m} - \gamma \left( \frac{K_c}{2m} \right)^2 \right]\), with \(L_c\) the weight of the edges within community \(c\), \(K_c\) the sum of the degrees (strengths) of its nodes and \(m\) the total edge weight;

  • directed (Leicht and Newman, 2008): \(Q = \sum_c \left[ \frac{L_c}{m} - \gamma \frac{K^{out}_c K^{in}_c}{m^2} \right]\);

  • bipartite (Barber, 2007): the null model only joins nodes of different types, \(Q = \sum_c \left[ \frac{L_c}{m} - \gamma \frac{K^{(0)}_c K^{(1)}_c}{m^2} \right]\), with \(K^{(0)}_c\) and \(K^{(1)}_c\) the degrees of its nodes of each type (directed bipartite networks use the directed variant);

  • multilayer (Mucha et al., 2010): each layer has its own null model (its own \(m_l\) and degrees, with \(\gamma\) the same for all layers), and couplings and other interlayer edges add their weight when both ends are in the same community, without a null model term: \(Q = \frac{1}{2\mu} \sum \left[ (A_{ij} - \gamma \frac{k_i k_j}{2 m_l}) \delta_{l_i l_j} + C_{ij} \right] \delta(g_i, g_j)\), with \(2\mu\) the total weight of intra-layer and interlayer edges (both directions); directed networks use the directed null model in each layer. With one layer and no interlayer edges this is the ordinary modularity.

Communities can overlap: a node in several communities has a list, tuple or set of labels (see Networks and their attributes). Overlapping modularity then weighs every pair of nodes by their belonging to each community they share, in the same variants (directed, bipartite, multilayer), following overlap:

  • "shen" (Shen et al., 2009): a node in \(O_i\) communities belongs to each with \(a_{ic} = 1 / O_i\), and \(Q = \frac{1}{2m} \sum_c \sum_{ij} \left[ A_{ij} - \gamma \frac{k_i k_j}{2m} \right] a_{ic} a_{jc}\). Without overlaps this is the modularity above;

  • "nicosia" (Nicosia et al., 2009): belonging \(\alpha_{ic} = 1 / O_i\) (0 outside the community) enters through \(g(\alpha) = 1 / (1 + e^{-(2 p \alpha - p)})\), with \(p = 30\) as in the paper, and \(Q = \frac{1}{2m} \sum_c \sum_{ij} \left[ g_{ic} g_{jc} A_{ij} - \gamma G_c^2 \frac{g_{ic} k_i g_{jc} k_j}{2m} \right]\), with \(G_c\) the mean of \(g_{jc}\) over all nodes (of the layer). It is sharper than Shen’s (a node in 3 communities barely belongs to any) and, unlike it, it differs from the classic modularity even without overlaps (its null model shrinks by \(G_c^2\)); it is used whenever asked.

A self loop counts once in \(L_c\) and twice in the degree of its node (in undirected networks), and parallel edges add up, as in NetworkX and igraph. resolution (\(\gamma\)) above 1 favors smaller communities. Modularity is at most 1; it is 0 for a single community containing everything (with \(\gamma = 1\)). NaN if there are no edges. The computation is one pass over the edges, on the device of the network.

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network.

  • partition – The communities: name of a node attribute, dictionary (or Series) from node id to label, or sequence of labels in network wide node order (see the module description).

  • weight – Edge attribute used as weight, or None for unit weights.

  • resolution – Resolution \(\gamma\).

  • component – Index of the component (0 is the largest), or None for the whole network.

  • overlap – Overlapping modularity: "shen" (used only if some node is in several communities; otherwise it is the classic modularity) or "nicosia".

Returns:

The modularity, a float.

Raises:

  • ValueError – If a node has no label, a sequence has the wrong length, or overlap is not valid.

  • KeyError – If there is no such node or edge attribute.

Example:

import graphoskop as gsk

net = gsk.load_network("edges.tsv", "nodes.tsv")            # nodes.tsv has a "party" column
gsk.modularity(net, "party")
gsk.modularity(net, {"alice": 0, "bob": 0, "carol": 1, ...})
gsk.modularity(net, labels, weight = "weight", resolution = 0.5)
gsk.modularity(net, {"alice": [0, 1], "bob": 0, "carol": 1, ...})   # alice in both communities
gsk.modularity(net, "community", overlap = "nicosia")
graphoskop.out_degree_fraction(net, partition, kind='average', community=None, weight=None, aggregate='mean', component=None)

Out-degree fraction of communities (Yang and Leskovec, 2012): how much of the degree of the nodes of a community points outside it. For a node \(u\) of community \(S\), the fraction is \(f_u = \frac{d_u - d_u^S}{d_u}\), with \(d_u\) its degree (strength) and \(d_u^S\) the part of it towards nodes of \(S\); kind gives, for the community:

  • "maximum": the largest \(f_u\) among its nodes;

  • "average": the mean \(f_u\) over its nodes;

  • "flake" (Flake et al., 2000): the fraction of its nodes with more weight outside the community than inside (\(d_u^S < d_u / 2\)).

All are between 0 and 1; the lower, the better. Nodes without edges count 0. Directions are ignored and self loops dropped; parallel edges add their weights. In a cover every community is the set of its nodes.

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network.

  • partition – The communities, as for modularity() (a cover is allowed).

  • kind – "maximum", "average" or "flake".

  • community – Label of a community, to get its value only.

  • weight – Name of the edge attribute used as edge weight, or None for unit weights.

  • aggregate – Overall value, without community, as for conductance().

  • component – Index of the component (0 is the largest), or None for the whole network.

Returns:

A float, or a pandas.Series.

Raises:

  • KeyError – If there is no such community or attribute.

  • ValueError – If kind or aggregate are not valid, or as modularity().

Example:

gsk.out_degree_fraction(net, "party")                       # average, mean over the parties
gsk.out_degree_fraction(net, "party", kind = "flake", aggregate = None)

Similarity of partitions

Two partitions of the same nodes (for instance, communities found and planted ones, or the results of two methods) are compared by information theory (normalized and adjusted mutual information) or by pairs of nodes (adjusted Rand index). Normalized mutual information and the adjusted Rand index also compare covers, with overlapping communities: by the overlapping normalized mutual information (McDaid et al., or Lancichinetti et al.) and by the Omega index.

gsk.normalized_mutual_information(net, "community", "found")
gsk.normalized_mutual_information(net, "community", "found", average = "max")
gsk.adjusted_mutual_information(net, "community", "found")    # corrected for chance
gsk.adjusted_rand_index(net, "community", "found")
gsk.normalized_mutual_information(net, "cover", "found", overlap = "lfk")   # a node in several communities
gsk.adjusted_rand_index(net, "cover", "found")                             # Omega index
graphoskop.adjusted_mutual_information(net, partition1, partition2, average='arithmetic')

Adjusted mutual information between two partitions of the nodes (Vinh, Epps and Bailey, 2010): the mutual information corrected for chance,

\[AMI = \frac{I(X; Y) - E[I]}{\mathrm{mean}(H(X), H(Y)) - E[I]},\]

with \(E[I]\) its expected value between random partitions with the same community sizes (hypergeometric model). 1 if the partitions are the same, about 0 (possibly negative) if they are independent: unlike normalized_mutual_information(), it does not grow with the number of communities. average as for normalized_mutual_information(). As in scikit-learn. There is no adjusted variant for overlapping communities: covers raise an error.

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network.

  • partition1 – The first partition, as for normalized_mutual_information().

  • partition2 – The second partition.

  • average – Mean of the entropies in the denominator.

Returns:

The AMI, a float.

Raises:

ValueError – If average is not valid, a node has no label, or several.

Example:

gsk.adjusted_mutual_information(net, "community", "found")
graphoskop.adjusted_rand_index(net, partition1, partition2)

Adjusted Rand index between two partitions of the nodes (Hubert and Arabie, 1985): the fraction of pairs of nodes on which the partitions agree (together in both, or apart in both), corrected for chance,

\[ARI = \frac{\sum_{ij} \binom{n_{ij}}{2} - \sum_i \binom{a_i}{2} \sum_j \binom{b_j}{2} / \binom{n}{2}} {\frac{1}{2} [\sum_i \binom{a_i}{2} + \sum_j \binom{b_j}{2}] - \sum_i \binom{a_i}{2} \sum_j \binom{b_j}{2} / \binom{n}{2}},\]

with \(n_{ij}\) the nodes in community \(i\) of one and \(j\) of the other, and \(a_i\), \(b_j\) the community sizes. 1 for the same partition, about 0 (possibly negative) for independent ones.

If some node is in several communities, the Omega index is used (Collins and Dent, 1988), its generalization to covers: two partitions agree on a pair of nodes when the pair shares the same number of communities in both, and Omega is the fraction of agreeing pairs corrected for chance (given how many pairs share 0, 1, 2, … communities in each). Without overlaps it equals the adjusted Rand index.

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network.

  • partition1 – The first partition, as for normalized_mutual_information(); a node can have several labels.

  • partition2 – The second partition.

Returns:

The adjusted Rand index (or Omega index), a float.

Raises:

ValueError – If a node has no label.

Example:

gsk.adjusted_rand_index(net, "community", "found")
gsk.adjusted_rand_index(net, "cover", "found")       # Omega index
graphoskop.normalized_mutual_information(net, partition1, partition2, average='arithmetic', overlap='mcdaid')

Normalized mutual information between two partitions of the nodes (or covers, with overlapping communities): 1 if they are the same (up to the labels), close to 0 if independent.

For partitions, \(NMI = I(X; Y) / \mathrm{mean}(H(X), H(Y))\), with \(I\) the mutual information and \(H\) the entropy of the community sizes; average is the mean in the denominator ("arithmetic", as in scikit-learn, "geometric", "max" or "min").

If some node is in several communities, of either partition, the overlapping variant is used: every community is a binary variable over the nodes (in it or not), each community of one cover is explained by the community of the other that leaves the least uncertainty on it, among those that agree with it more than they disagree (Lancichinetti, Fortunato and Kertész, 2009): a community much smaller than any community of the other cover containing it stays unexplained, so covers that merge many communities score low. With overlap:

  • "mcdaid" (McDaid, Greene and Hurley, 2011): the conditional entropies of the communities are summed, \(I = \frac{1}{2} [H(X) - H(X|Y) + H(Y) - H(Y|X)]\) and \(NMI = I / \max(H(X), H(Y))\);

  • "lfk" (Lancichinetti, Fortunato and Kertész, 2009): \(NMI = 1 - \frac{1}{2} [H(X|Y)_{norm} + H(Y|X)_{norm}]\), with the conditional entropy of every community divided by its entropy and averaged over the communities of the cover.

Only pairs of communities sharing nodes are compared. The overlapping variants differ from the classic one even without overlaps.

Hypergraphs and simplicial complexes: not supported (see Higher-order networks).

Parameters:

  • net – A Network.

  • partition1 – The first partition: name of a node attribute, dictionary (or Series) from node id to label, or sequence of labels in network wide node order, as for modularity(); a node can have several labels.

  • partition2 – The second partition, in the same forms.

  • average – Mean of the entropies in the denominator, for partitions.

  • overlap – Variant for covers: "mcdaid" or "lfk".

Returns:

The NMI, a float.

Raises:

ValueError – If average or overlap are not valid, or a node has no label.

Example:

import graphoskop as gsk

net = gsk.lfr_benchmark_graph(n = 1000, mu = 0.3, seed = 0)        # planted "community"
gsk.leiden_communities(net, attribute = "found", seed = 0)
gsk.normalized_mutual_information(net, "community", "found")
gsk.normalized_mutual_information(net, "cover", "found", overlap = "lfk")
